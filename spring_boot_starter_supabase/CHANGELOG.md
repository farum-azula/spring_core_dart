## Unreleased

- `SupabaseRateLimitStore.verify()`: at startup the store calls its database function once, for a bucket of its own (`spring:verify`). A function or a table the project does not have, a function that answers something else, or a service role that may not call it, fails the start with what to run (`sql/rate_limit.sql`); a project that cannot be reached is a warning. In an edge function the start is the first request of an instance, which then costs one call more; `spring.web.rate-limit.verify-store=false` skips it.
- Fixed: `@Cacheable(..., key: ..., sync: true)` on a cache of the Supabase resolver shared one run of the method between callers that missed the same key at once, so a user could get the rows read as another user. The calls in flight are kept apart per caller now (`KeyScopingCache` of the cache starter).
- Fixed: a value of a `@PostgresChanges` filter (`PostgresFilterEncoder`) with a `{` or `}` in it, or the word `null`, is put in double quotes. Realtime reads the values of `in.(…)` as an array of PostgreSQL: unquoted, a brace made the subscription an error or one that matched no row, and `null` matched no row, without a word. An empty value is refused with an `ArgumentError` (it was sent as `""`, which matches no row): Realtime's filter cannot say it.
- Fixed: Realtime after the login changed to another user, or to nobody: the channels in use are joined again with the new token (the anon key after a logout), and what the server still sends for the user before is dropped. They were only sent the new token, and for a moment after it the server went on sending the rows the user before may read, to the listeners of the new one. A new token of the same user is still sent without a new join. A login that changes while a channel is being joined now reaches it right after the join, not at the next heartbeat.
- Fixed: caches (`SupabaseCacheResolver`): a call looks up and stores under one caller, who calls when it begins, and stores nothing when the caller is another one by the time its answer is there. With an explicit `key:` the answer of a call during which the login changed was stored under the new caller's key, though it could be the rows of the one before.
- Fixed: a query over the REST API that asks for every row (`findAll()`, a derived `findBy…` returning a list), or for more than the API returns in one answer (the project's "Max rows", 1000 by default), got only that many, without any sign of it. An answer that long is now read on in further calls, ordered by the id last (`spring.supabase.db.max-rows`, default 1000: set it to the project's value when that one was changed); an entity without an id fails with an explanation instead. The rows a database function returns (`@Procedure`) are still cut there.
- `spring.supabase.db.rls: user` is refused through port 6543 on any address (a project's dedicated pooler, a self-hosted one), not only on `*.pooler.supabase.com`: a transaction pooler keeps no session, so a role set for one user could serve another's statement.
- `spring.supabase.db.rls: user` is refused when `spring.datasource.url` is another address than `spring.supabase.db.url`: the statements would run as the user of that address, past row-level security, while the start said it applies.
- While a server handles a request, the caller is the request's (its bearer token, or nobody), never the login of the process (`SupabaseAuth`): an endpoint that signs a user in, or a restored session, no longer becomes the caller of everybody else's requests.
- A session that ends while its token is asked for (the refresh was refused) fails the call with `CredentialsExpiredException`; the call no longer goes on with the anon key.
- `SupabaseRateLimitStore`: the web starter's rate limiter keeps its buckets behind one database function, called through the REST API as the service role (`spring.web.rate-limit.store: procedure`, the default of an application on the REST path when the rate limiter is on; what an edge function uses). The table (`unlogged`, closed to `anon` and `authenticated`) and the function `rate_limit_acquire(p_key, p_capacity, p_refill_per_second, p_permits)` are in `lib/sql/rate_limit.sql`, to copy into the project's migrations; `spring.supabase.rate-limit.function` names the function.
- The first version: Supabase for spring_boot_dart, on a server and in Flutter apps, with a client of its own (no third-party package; it compiles to WebAssembly). Not on pub.dev yet: a git dependency until its tests against the whole of Supabase have run. Its tests: without a network, on PostgreSQL and PostgREST in containers (its own pipeline), and against a whole stack (written, not in a pipeline yet).
- `SupabaseCredentials` (the bean `supabaseCredentials`): the one place every call takes its key and token from (the service role inside `asServiceRole`, else the signed-in user of the application, else the bearer token of a server's request when it is a user's token of this project, else the anon key), and `SupabaseHttp`, the client under every part (the key and the token on each call, never a redirect followed, an `Observation` per call, logs without keys, tokens or query values).
- Data through Spring Data: the store `supabase` (`PostgrestDataStore`) over the project's REST API, the default without `spring.supabase.db.url`: derived queries as filters (text patterns as anchored expressions with the text escaped, values in lists and `Or` groups quoted), `Sort`, pages with an exact count, `@Version` as a filtered update, database functions with `@Procedure`, the database's errors as the data starter's exceptions; the build knows the store (`@DataStoreDeclaration`), so a repository on it with `@Lock`, a SQL `@Query` or `@Transactional`, and a `@Transactional` bean when it is the default store, fail the build (with only `spring.supabase.db.url` set the build cannot tell the default store, and the check is at startup). With `spring.supabase.db.url` the repositories use SQL over it (transactions, `@Lock`, SQL `@Query`), and `spring.supabase.db.rls: user` runs every transaction and statement as the current user (`SupabaseRlsSessionHook`), refused through the transaction pooler.
- Data: a property marked `@Json` (spring_boot_starter_data) is sent to and read from the REST API as nested JSON, for a `jsonb` or `json` column; over `spring.supabase.db.url` it is PostgreSQL's `jsonb` / `json`.
- Security: on a server the defaults of Spring Security's resource server (the project's JWKS with ES256 and RS256, or `spring.supabase.auth.jwt-secret` with HS256; the exact issuer, the audience and the role `authenticated`; roles from `app_metadata.roles` only; `require-expiry`: a token without `exp` is refused), which the application's own properties override; `SupabaseAuth`, the login of a client application as a `LoginSession`.
- Storage: `StorageTemplate` (upload, download as a stream, JSON through the `ObjectMapper`, public and signed URLs, signed uploads, list, delete, move, copy, exists, info, buckets, `asServiceRole()`) and declared buckets (`@StorageBucket` with `@Upload`, `@Download`, `@SignedUrl`, `@PublicUrl`, `@StorageObject`, `@DeleteObject`), whose paths take `${property}`, `{parameter}` and SpEL in `#{...}`; a value is one segment of a path and cannot leave its folder.
- Edge Functions: `@EdgeFunctions` interfaces with `@EdgeFunction('name')`, Feign clients of `<url>/functions/v1` with the key and the token of the credentials; a function may answer JSON or text, a file (`Uint8List`), server-sent events (`EventStream<T>`), the body as it arrives (`Stream<List<int>>`) or status and headers (`ResponseEntity<T>`); a request body is read whole.
- Realtime: `SupabaseRealtime` over the WebSocket starter's Phoenix Channels client (changes of rows, broadcast, presence), `@RealtimeChannel` interfaces, and repository methods `watchBy…` and `changesBy…`. The repository streams subscribe to the whole table and apply their conditions on this side (a filter of Realtime sends no delete and no update that takes a row out of it): a delete arrives as its id only, and every delete of the table concerns every stream unless the table has `replica identity full`.
- Caches: `SupabaseKeyGenerator` and `SupabaseCacheResolver` keep the entries of every caller apart (the anon key, each user, the service role), whether the key comes from the generator or from `key:`; the caches of `spring.supabase.cache.shared` are the same for everyone.
- At startup: how the repositories reach the database (never a password), a warning for the transaction pooler, and in a client application a warning for each key or password that ships in it (`service-role-key`, `db.url`, `auth.jwt-secret`).
- An example application, `example/supabase` of the repository: a Flutter app and a server on one project, with the project for the Supabase CLI.
