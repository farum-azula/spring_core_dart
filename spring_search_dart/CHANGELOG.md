## Unreleased

- A hit's highlights are found when first asked for (`SearchHit.lazy`): a search finds them for the hits shown, not for every document that matched, which with an index read from its file analyzed every one of them again (800 ms on a slow laptop for a common word). The index file is a line per piece (format 2), read with a pause every few milliseconds (`SearchIndex.fromJsonParts`), so reading it does not hold the thread that draws.
- The index the build writes (`spring.search.prebuilt`, on by default): for the pages of `spring.search.markdown` the generator writes the index of each language to `lib/resources/spring_gen/search/<language>.json` (a Flutter asset, never embedded), and the `SearchService` reads it instead of reading every page and building the index: one download and a fraction of a second instead of hundreds of files and seconds of work on the thread that draws. A file is used only when its analyzer and its Markdown entries are the app's, and not when the app has sources of its own for that language. `SearchIndex.toJson`/`SearchIndex.fromJson`, `SearchIndexFiles`, `SearchIndexWriter` and `bin/search_index.dart` (what the generator runs); a term's postings are decoded when a search first needs them.
- `LanguageSearchDocumentSource`: a source that knows its languages before reading; `MarkdownSearchSource` is one, and the search reads only the files of the language searched (and the default language's for a page without a translation), so a site whose pages are downloaded fetches those of one language. A location of any root (`asset:docs/**/*.md`) gives its paths relative to its folder.
- The documents are read once and the index of a language is built when that language is first searched: a search waits for its own language only (`SearchService.isIndexed(language)`, `prepare(language:)`).
- `spring.search.indexing: background`: the indexes build right after the start, while the app runs, the default language first.
- `spring.search.indexing` (`first-search` by default, `start`): `start` builds the indexes while the application starts (the `searchIndexRunner`, an `ApplicationRunner`), so a Flutter app builds them behind its splash. `SearchService.prepare()` starts the build now (when the search opens) and `prepared` tells whether it started; a search waits for the same build.
- The indexes build a few dozen documents at a time with a pause between (`SearchIndex.buildAsync`), so an app keeps drawing its frames while they build: the first search no longer freezes the screen. Reading the documents pauses the same way, since resources held in memory give their text without a real pause.
- `SearchRanker.rank` gets the `SearchQuery` searched (`rank(hit, score, query)`): a ranker can put the page whose name the query is first, which the hit alone cannot tell.
