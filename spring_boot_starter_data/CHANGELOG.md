- PostgreSQL (step 4), through the application's `postgres` package: the generator writes a thin glue (`PostgresBinding` over the package, the bean `postgresJdbcDriver`; run it again) and the starter's `PostgresJdbcDriver` and `PostgresDialect` do the rest. `spring.datasource.url=postgresql://user:password@host:5432/db?sslmode=require` (also `jdbc:postgresql://…`); the URL's `sslmode` (default `prefer`: TLS, then plain text when the server has none; `verify-ca` and `verify-full` check the certificate and host name, `ssl-root-cert` names the authorities), `sslrootcert`, `connect_timeout`, `application_name` and `currentSchema` are read, any other parameter is an error, and `spring.datasource.postgresql.*` (or `postgres.*`) sets the same, and wins. `?` becomes `$1` outside quotes, comments and `$$` (`??` is a literal `?`); queries and updates bind values, streams cancel without breaking the connection, a generated id is `BIGINT GENERATED BY DEFAULT AS IDENTITY` read back with `RETURNING`, transactions have every isolation level (read uncommitted runs as read committed) and `READ ONLY`, `nested` uses savepoints, a statement timeout is cancelled on the server, DDL is transactional and the migrations of several instances queue on an advisory lock. `@Lock` is `FOR UPDATE` / `FOR SHARE` with `NOWAIT` (zero timeout), `SKIP LOCKED` and `SET LOCAL lock_timeout`. Errors by SQL state: `23505` `DuplicateKeyException`, other `23xxx` and `22xxx` `DataIntegrityViolationException`, `40001` `CannotSerializeTransactionException`, `40P01` `DeadlockLoserDataAccessException`, `55P03` `CannotAcquireLockException`, `57014` `QueryTimeoutException`, `42601` / `42P01` / `42703`… `BadSqlGrammarException`, `08xxx`, `28xxx`, `53xxx`, `57P01` `DataAccessResourceFailureException`; the messages keep what the server says about the statement, never the `DETAIL` line, a rejected value, a bound value or a password. Schema creation and validation (`information_schema`, `pg_catalog`: types, foreign keys with their `ON DELETE`, unique keys), `TIMESTAMPTZ` read in UTC, `BIGINT`, `TEXT`, `BOOLEAN`, `DOUBLE PRECISION`, `BYTEA`, `NUMERIC` for `BigInt`. Text is ordered by the database's collation, and `ON DELETE RESTRICT` is checked when the statement ends. Documented in `docs/configuration.md`, section 20; the tests tagged `postgres` run on a server when `SPRING_TEST_POSTGRES_URL` is set (CI uses a service container).

- SQL databases from properties (step 3): `spring.datasource.*` (and `spring.datasources.<name>.*`) make the `DataSource` pool (`spring.datasource.pool.*`), a `DataSourceTransactionManager` (the `transactionManager`, in place of the in-memory one), `JdbcTemplate`, `NamedParameterJdbcTemplate` and `JdbcClient` beans, for the primary database and for each named one (qualified, fallbacks); the driver is chosen by the URL's scheme among the `JdbcDriver` beans the generator writes, `spring.datasource.sqlite.base-directory` and `busy-timeout` reach the SQLite driver per data source.
  - The schema (migrations, scripts, validation, `create` / `create-drop`) is set up at startup, before any repository, `JdbcTemplate`, runner or `@PostConstruct` can use the database: the data source waits for it before its first connection.
  - `spring.jdbc.template.query-timeout`, `spring.data.jdbc.show-sql`, `format-sql`, `show-parameters`, `slow-query-threshold`.
  - Startup failures are explained (`APPLICATION FAILED TO START`): a URL no driver handles (what package to add), two drivers for one scheme, a failed migration, a schema that does not fit the entities, a database that cannot be reached.
  - Repositories without `@UseStore` use `jdbc` once a primary data source exists.
  - SQLite through the application's `sqlite3` package: the generator writes a thin glue, the starter's `SqliteJdbcDriver` and `SqliteDialect` do the rest (transactions, savepoints, one statement at a time per connection, error translation: duplicate key, constraint, busy, wrong SQL).
  - The JDBC layer: `PooledDataSource`, `DataSourceTransactionManager`, `JdbcTemplate`, `NamedParameterJdbcTemplate` (`:name`, lists expanded for `IN`), `JdbcClient`, `RowMapper`, `DataClassRowMapper` (columns by name into an introspected class), `ResultSetExtractor`.
  - Repositories on SQL: derived queries become SQL with the in-memory store's semantics (one test suite runs on both); `@Query` with named parameters, `:#{...}` SpEL, `#{#entityName}`, `${...}` properties, DTO results, `Page` / `Slice`, `@Modifying`, `rowMapper` / `resultSetExtractor`; values are always bound, never written into the SQL.
  - Schema: `spring.sql.init.*` scripts, migrations (`lib/resources/db/migration/V<n>__<name>.sql`, `R__<name>.sql`, `spring.sql.migration.*`, history in `schema_history`, checksums, one instance migrates while others wait), `spring.data.jdbc.schema` = `validate` (default) / `create` / `create-drop` / `none`.
  - SQL logs after Spring's loggers (`spring.jdbc.core.JdbcTemplate` debug, values at trace in `StatementCreatorUtils`, masked), slow statements at warn.
  - References between aggregates: `@Reference(Author) int authorId` next to `AggregateReference<Author, int>` (the id type is checked against the target's `@Id`; a field of an entity type without `@MappedCollection` is refused with a hint), foreign keys and an index for every reference in created schemas, `@OnDelete(OnDeleteAction.noAction / restrict / cascade / setNull / setDefault)` (`setDefault` writes no default yet: the column becomes null; a later version checks the default exists), `@Unique()` and `@UniqueConstraint([...], name:)` (`uq_<table>_<columns>`). A referenced aggregate's table is created and validated with the referencing one.
  - The in-memory store enforces them exactly as SQLite with `foreign_keys = ON` does (`DataIntegrityViolationException` for a missing target or a refused delete, `noAction` checked at the end of the statement and `restrict` row by row, cascades and `setNull` recursive, also for child rows, inside the transaction, with row locks; `DuplicateKeyException` for a unique violation, nulls never conflict); a statement is all or nothing.
  - Schema validation checks foreign keys (an explicit `@OnDelete` not matched is an error, a plain reference without a key a warning) and unique keys (`sqlite_autoindex_*` included) through the new dialect hooks `describeForeignKeys` and `describeUniqueKeys`; tables are created after the ones they reference, a cycle works (`SqlDialect.supportsForwardForeignKeys`, `addForeignKeyStatement`, `beforeDropStatements`, `dropTableStatement` for databases that need `ALTER TABLE`), and `create-drop` always drops.
  - SQLite's `ignoreCase` folds every letter (`Ä` / `ä`) like the in-memory store: the driver registers `spring_lower` (Dart's `toLowerCase`) on each connection, `SqlDialect.lower` writes it; `SqliteDatabase.createFunction` is new in the glue (run the generator again).
  - SQLite on an isolate of its own: `spring.datasource.sqlite.isolate=true` (per data source, or `SqliteJdbcDriver(isolate: true)`) opens each connection's database inside a worker isolate through the same binding and sends every statement as a message, so the synchronous calls no longer hold the caller's isolate (Flutter's UI, a server's event loop). Transactions, savepoints, read-only mode, the functions the driver registers, streams (read in batches, the cursor closed when the stream is cancelled) and errors (types and messages kept, the worker's stack trace as text) behave as in the caller's isolate, and the driver and error test suites run in both modes. A worker that dies fails the pending and later statements with a `SqlError` (`connectionLost`) instead of hanging; an idle connection nobody closed does not keep the process alive. The starter's Flutter counterpart turns it on and sets `spring.datasource.sqlite.base-directory`.
- Transactions (step 2):
  - `@Transactional` on bean methods (through the generated proxies) with Spring's seven propagations, isolation, timeout, read-only, `rollbackFor` / `noRollbackFor` matching subtypes (every exception rolls back by default: Dart has no checked exceptions); `TransactionTemplate`; `PlatformTransactionManager`, `AbstractPlatformTransactionManager`, `TransactionSynchronization`.
  - The current transaction lives in a `Zone`: it follows `await`, two concurrent requests never share one, `requiresNew` / `notSupported` set aside only their own store's transaction, and work started without `await` that outlives its transaction fails instead of running outside it.
  - The in-memory store has transactions: read committed, row locks with deadlock detection and a lock timeout (`spring.data.memory.lock-timeout`, 10s), savepoints (`nested`), read-only transactions refusing writes; `InMemoryTransactionManager` is the default `transactionManager`, one more per `@UseDataSource` name.
  - `@Lock(LockMode.pessimisticWrite / pessimisticRead, timeout:, skipLocked:)` on derived `find` methods and `findById`, only inside a transaction.
  - Repository writes (`save`, `saveAll`, deletes) run in a transaction: `saveAll` and an aggregate with its children are atomic; inside an outer transaction they join it.
  - A `@Transactional` method must return a `Future`: a synchronous or `Stream` method, an unknown or ambiguous transaction manager stop the start.
- First version: Spring Data for Dart on Spring Data JDBC's model, with an in-memory store (SQLite and PostgreSQL come next).
  - Entities: `@Table`, `@Id`, `@Column`, `@Transient`, `@Version`, `@CreatedDate`, `@LastModifiedDate`, `@CreatedBy`, `@LastModifiedBy` (`@EnableDataAuditing`, `AuditorAware`), `@MappedCollection` children saved and deleted with their root, `AggregateReference` to other aggregates.

  - `Sort`, `SortOrder`, `Pageable`, `PageRequest`, `Page`, `Slice`.
  - Optimistic locking with `@Version`: `OptimisticLockingFailureException` on a conflict.
  - Spring's `DataAccessException` hierarchy.
  - Logs: statements at debug; values only at trace, with names that look secret (`password`, `token`, `secret`, `key`) masked.
